# Woodpecker secrets from gopass (GPG export unlock)

## Goal

- Hold all pipeline secrets in gopass. Hold one key only in Woodpecker: base64 GPG private export (`gpg_export_b64`) + passphrase (`gpg_passphrase`).
- Cover both paths: server-side Woodpecker builds and local `mise run wp:build` (`woodpecker-cli exec`). Same store layout, same secret names.
- Store `cosign.key` PEM in gopass. Never commit key material. Key exists transiently in `/tmp` only, mode `600`, removed after use.

## Current state (repo)

- `.woodpecker/build.yml:41-64` consumes native secrets via `from_secret`: `registry_user`, `registry_password`, `cosign_key` (PEM content), `cosign_password`.
- `.mise/tasks/wp/build:4-14` supports `--secrets-file`, default `.woodpecker/local-secrets.yaml`. Warns when missing. File is gitignored (`.gitignore:4`).
- `.gitignore:6` ignores `cosign.key`. `AGENTS.md` forbids committing `cosign.*` secrets.
- `recipes/base/gopass.yml:8-9` ships `gopass` + `gopass-jsonapi`. Init task at `files/base/gopass/usr/lib/kierownik/tasks/gopass/init` runs `gopass setup` + Brave jsonapi wiring.
- GPG helper tasks exist under `files/base/system/usr/lib/kierownik/tasks/gpg/` (`init`, `copy-sign-pub`, `copy-ssh-pub`, `reload-agent`). `copy-sign-pub` extracts `[S]` subkey; password-store encryption needs an `[E]`-capable key — verify on host before finalizing commands.
- No store remote documented. No fetch step exists. No secret-extension broker exists.
- GHA (`.github/workflows/build.yml:39`) uses `secrets.SIGNING_SECRET`; out of scope.

## Design

Pick: in-pipeline fetch. Cheapest robust option for single-host setup. No extra service to host.

Rejected alternative (documented only): secret-extension broker implementing Woodpecker secret-extension protocol (`POST {repo, pipeline} -> {secrets[]}`, ed25519-signed). Requires Woodpecker >= 3.14 (secret extension endpoint, currently RC-era), `WOODPECKER_SECRET_EXTENSION_ENDPOINT` + `WOODPECKER_EXTENSIONS_ALLOWED_HOSTS` wiring, broker hardening, log-masking gaps remain. Revisit only if fleet grows past one repo/host.

### 1. Store layout

```text
woodpecker/registry_user       # plaintext login
woodpecker/registry_password   # registry token
woodpecker/cosign_key          # full PEM, multiline, byte-exact
woodpecker/cosign_password     # empty or key passphrase
woodpecker/store_repo          # git URL of password-store (optional; else hardcode pipeline env)
```

- GPG recipient: existing personal key. Confirm encryption subkey (`gopass` encrypts to `[E]` recipient, not the `[S]`-only sign subkey).
- `gopass show -o <path>` is the only read path. No `gopass show` without `-o` in scripts (avoids terminal leaks).

### 2. Server pipeline flow

New step `fetch-secrets` runs before `build-push` in `.woodpecker/build.yml`:

1. Image with `gopass` + `git` + `gnupg` (e.g. `alpine` with `apk add`, or extend `ghcr.io/blue-build/cli:latest` step with install prelude).
2. Inputs: two native secrets only — `gpg_export_b64`, `gpg_passphrase` — via `from_secret`. Restrict with image allowlist + `events: [push, manual, cron]`; never `pull_request` (fork PRs must not receive unlock material).
3. Step logic:
   ```sh
   echo "$GPG_EXPORT_B64" | base64 -d | gpg --batch --import
   git clone "$STORE_REPO" ~/.password-store   # or: gopass clone "$STORE_REPO"
   mkdir -p .woodpecker/.run-secrets && chmod 700 .woodpecker/.run-secrets
   gopass show -o woodpecker/registry_user > .woodpecker/.run-secrets/registry_user
   gopass show -o woodpecker/registry_password > .woodpecker/.run-secrets/registry_password
   gopass show -o woodpecker/cosign_key > .woodpecker/.run-secrets/cosign.key
   gopass show -o woodpecker/cosign_password > .woodpecker/.run-secrets/cosign_password
   chmod 600 .woodpecker/.run-secrets/*
   ```
   Multiline PEM must survive byte-exact; prefer `@`-file secret loading (`woodpecker-cli repo secret add -value @path`) patterns where CLI is involved.
4. Downstream handoff via workspace files, not env: `build-push` reads `registry_user`/`registry_password` from files; `sign-cosign` copies `cosign.key` to `/tmp/cosign.key`, `chmod 600`, signs, `rm -f`. Existing `echo > /tmp/cosign.key` lines (`.woodpecker/build.yml:67-70`) keep shape, source changes from env var to workspace file.
5. Log hygiene (Woodpecker does not mask external secrets in step logs): forbid `echo $SECRET`, `set -x`, `env`, debug dumps in fetch/build/sign steps. Fail closed when any store entry missing.

### 3. Local exec flow

- New task `.mise/tasks/wp/secrets-from-gopass` (`#!/usr/bin/env bash`, `set -oue pipefail`, `gum` for UX only, never `echo`/`read -p`): reads 4 paths via local GPG agent, writes ephemeral YAML `--secrets-file` (mode `600`), `trap rm -f` after `woodpecker-cli exec` returns.
- `.mise/tasks/wp/build` auto-uses temp file when `gopass ls woodpecker/...` succeeds; falls back to existing `--secrets-file` flag behavior otherwise.
- No export key on disk locally. Agent unlock only.

### 4. Security notes

- `gpg_export_b64` + `gpg_passphrase` become the only long-lived secrets in Woodpecker DB. Rotation: re-export, `woodpecker-cli secret add`, revoke old material.
- `cosign.pub` stays committed; `cosign.key` never committed.
- Event filter excluding `pull_request` is mandatory, not optional.

## Validation

- `mise run check:lint`
- Local: `gopass ls woodpecker`, temp YAML parses + mode `600`, `mise run wp:build --event manual` succeeds, temp file removed afterwards.
- Server: push on test branch — registry login resolves, image pushes, `cosign sign` succeeds, `cosign verify --key cosign.pub <image>:latest` passes.
- Negative: `pull_request` event receives no secrets; missing store entry fails closed with clear error; no secret values in step logs / `journalctl`; `git status` shows no key material.
- Rotation dry-run: re-export GPG key, update 2 native secrets, confirm old export no longer works.
- PEM round-trip: `diff` of `gopass show -o woodpecker/cosign_key` against original `cosign.key` is empty.

## Non-goals

- No secret-extension broker service in v1 (see Design intro for threshold to revisit).
- No GHA / Vault / OpenBao migration.
- No per-PR secret access for forks.
- No `gum` in build-time scripts (`files/scripts/finalize/`); `gum` stays in `.mise/tasks/` and user tasks only.
